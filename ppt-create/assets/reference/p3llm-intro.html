Lab paper discussion · PIM for LLM decoding

P3-LLM

How does P3-LLM make DRAM processing-in-memory fast for small-batch LLM decoding?

It shrinks every operand to 4 or 8 bits in a format chosen per operand, so a small PCU with 4× the multipliers fits in the DRAM. That PCU runs twice per column read and uses each weight for two requests.

01 / 21Part 1 of 6 · Summary

Summary: P3-LLM keeps DRAM processing-in-memory fast at small batches by shrinking every operand and running a small compute unit twice per weight read.

The problem. An LLM writes text one token at a time, and every token reads every weight from DRAM. So decoding waits on memory bandwidth. PIM puts multipliers next to the DRAM banks to use their internal bandwidth. Today's PIM units compute in FP16 or BF16, and in a DRAM process they are large and slow. PIM therefore loses its edge already at batch 2–4 or with grouped-query attention (§II–III).

  1. W4A8KV4P8 formats. 4-bit weights and KV-cache, 8-bit activations and attention scores, each operand in its own number format (§IV).
  2. Low-precision PCU with TEP. 4× the multipliers in about the same area, clocked at tCCD_S instead of tCCD_L, so one weight read serves two inputs (§V-A, §V-D).
  3. Fused dequantization. The NPU folds each scale into a neighbouring operator, so PIM runs only low-precision math (§V-C).

02 / 21Part 2 of 6 · Background: DRAM and AiM

DRAM is a tree: a channel holds bank groups, a bank group holds banks, and a bank holds rows of columns.

A channel has its own command bus and data bus. The host drives each channel on its own.

A bank is one memory array. It can keep one row open at a time, in its row buffer.

A bank group is a set of banks that share one path to the channel's I/O. That shared path sets a timing rule on slide 5.

A row is what one ACT opens: 2,048 B in this preset. A column is what one read moves: 32 B here.

03 / 21Part 2 of 6 · Background: DRAM and AiM

Reading one column takes three commands: ACT opens a row, RD moves one column out, and PRE closes the row.

ACT is the expensive step. It moves a whole row from the cells into the sense amplifiers.

Once the row is open, each RD is cheap. The host can read many columns of the same row with no new ACT (frame 4).

PIM depends on this fact. It opens a row once and then computes on every column of it.

04 / 21Part 2 of 6 · Background: DRAM and AiM

Timing rules set the earliest moment for each command: tRCD after ACT, CL before the data, tRAS before PRE and tRP before the next ACT.

Before you press play: the host has a row open in bank group 0 and one in bank group 1. It wants a second read 2.5 ns after the first. Which bank group can that read go to?

Only bank group 1 (frame 5). A second read to bank group 0 needs tCCD_L = 5 ns, so it must wait (frame 4).

tRCD: from ACT to the first RD of that row. CL: from RD to the first data on the bus.

tRAS: the shortest time a row stays open. tRP: from PRE to the next ACT in the same bank.

tCCD: the shortest spacing between two column commands. Frames 4 and 5 show that it depends on the bank group.

All values here are simulator presets, not JEDEC table values.

05 / 21Part 2 of 6 · Background: DRAM and AiM

Two column reads in the same bank group must be tCCD_L apart; reads to different bank groups need only tCCD_S.

The four banks of a bank group share one I/O path. After one read, that path needs time before it carries the next. That time is tCCD_L.

Banks in different bank groups use separate paths. Their reads overlap, so the next read waits only tCCD_S, one burst on the bus.

In this preset tCCD_S is 2.5 ns and tCCD_L is 5 ns. P3-LLM notes that tCCD_S is about half of tCCD_L in every HBM generation (§V-D).

Keep this factor of two in mind: P3-LLM's TEP is built on it.

06 / 21Part 2 of 6 · Background: DRAM and AiM

Stock AiM computes inside the DRAM: one MAC16 command makes all 16 banks multiply one column of weights by the same input slice.

Before you press play: which of these commands use the data bus between the host and the DRAM?

WRGB (frame 1), WRMAC16 (frame 2) and RDMAC16 (frame 7). MAC16 (frame 5) moves nothing on the data bus: each bank sends its column to its own PU, and the input comes from the global buffer inside the chip.

Each bank has its own processing unit (PU). All PUs read the same input from one shared global buffer (GB). Each PU keeps its running sum in a MAC register.

Every MAC16 touches all four bank groups. So two MAC16s always fall under the same-group rule and go tCCD_L apart: stock AiM does one MAC command per tCCD_L.

07 / 21Part 2 of 6 · Background: DRAM and AiM

P3-LLM builds on Samsung's HBM-PIM, whose MAC idea is AiM's: multiply the open row's columns by an input held next to the banks.

HBM-PIM puts one PIM compute unit (PCU) between an even bank and an odd bank, so a channel has 8 PCUs (§V-A).

Each PCU is a 16-way SIMD FP16 MAC. One column access gives it 256 bits, 16 FP16 weights. It reuses one input element across all 16 weights (§II-B).

AiM differs in the details: one PU per bank, BF16 numbers, an adder tree and a global buffer.

From here on the slides use the paper's word, PCU.

08 / 21Part 3 of 6 · Motivation

An FP16 PIM unit hits its compute roof as soon as the batch reaches 2–4 or attention uses grouped-query attention.

Decoding is a GEMV. Each weight serves one multiply per request, so decoding is memory-bound and PIM's internal bandwidth helps (§II-B).

FP16 or BF16 PCUs take 20–27 % of the DRAM die. A DRAM process has about 10× lower transistor density than logic, so few PCUs fit (§II-B).

HBM-PIM's roof is 1.23 TOPS on 1.23 TB/s. A batch or GQA reuses each weight for more inputs and pushes the operator past the roof's corner (Fig. 4).

P3-LLM fits 4× the multipliers in the same compute area and clocks them 2× faster. Its roof is 8× higher, 9.84 TOPS (§III-B).

09 / 21Part 3 of 6 · Motivation

P3-LLM gives 4 bits to the large, robust operands and 8 bits to the small, fragile ones: W4A8KV4P8.

At batch 1 the weights fill most of the memory. As the batch grows, the KV-cache grows with it. Activations and scores stay small (Fig. 3a).

Activations and scores lose the most accuracy when quantized. Weights and KV-cache still work at 4 bits (Fig. 3b).

P3-LLM quantizes the scores too, so that P·V also runs on the low-precision PCU. Plain integers at W4A8KV4P8 lose too much, so each operand gets its own format (next four slides).

10 / 21Part 4 of 6 · Design · 1: formats

Key-cache outliers sit in a few fixed channels, so P3-LLM divides each channel by its prefill maximum and then stores 4-bit integers.

The value cache shows no outlier pattern. The key cache has a few outlier channels (Fig. 5).

During prefill, P3-LLM records each key channel's largest magnitude and divides the channel by it, so the channel fits in [−1, 1]. Decoding reuses the same factors (Eq. 2).

No calibration dataset is needed, so the method cannot overfit one. The factors take < 1 % of memory and < 5 ms for Llama-3.1-8B at 32K context on an A6000 GPU (§IV-A).

RoPE rotates keys by position. Llama-1/2 keys are quantized before RoPE; Llama-3 and Mistral keys after it, because their outlier channels survive RoPE.

11 / 21Part 4 of 6 · Design · 1: formats

Attention scores lie between 0 and 1, so P3-LLM drops the sign bit and gives it to the mantissa: FP8-S0E4M4.

Softmax outputs are never negative, so a sign bit carries nothing.

FP16 values below 1 use only 14 exponent values, −14 to −1. Four exponent bits with a bias of −15 cover them, which leaves 4 mantissa bits.

Quantizing needs no scale: P3-LLM rounds the FP16 score and keeps its top 4 mantissa bits.

Table II, Llama-3.1-8B on Wikitext: FP8-S0E4M4 gives perplexity 5.95, the same as FP16. INT8 gives 6.06 and FP8-E4M3 gives 5.99.

12 / 21Part 4 of 6 · Design · 1: formats

Weights use BitMoD: FP4 whose spare −0 code becomes one extra value, ±5 or ±8, chosen per group of 128 weights.

FP4 has 16 codes but only 15 values, because +0 and −0 are equal.

BitMoD maps −0 to one special value from {±5, ±8}. For each group of 128 weights it picks the value with the smallest error (§IV-C).

Weights and the KV-cache enter the PCU through the same input. So each PE has one decoder for both BitMoD and INT4-Asym (§V-A).

In the ablation, BitMoD instead of INT4 weights recovers 0.01 and 0.07 perplexity on Llama-2-7B and Llama-3.1-8B (Table VI).

13 / 21Part 4 of 6 · Design · 1: formats

Activations are cast straight to FP8-E4M3, whose wide range absorbs outliers without rotations or smoothing.

Activations also have outlier channels (§IV-D).

Rotations (QuaRot, SpinQuant) add work at run time. Smoothing (SmoothQuant) moves the difficulty into the weights, which hurts 4-bit weights.

A per-token cast to FP8-E4M3 has neither cost. With 4-bit weights it beats INT8 SmoothQuant on all four models: on Llama-3.1-8B, 6.16 against 6.36 (Table III).

14 / 21Part 4 of 6 · Design · 2: PCU and TEP

The low-precision PCU keeps HBM-PIM's 16 outputs but takes 4 inputs and 64 weights per column: a 1×4×16 dot-product tile.

A 256-bit column holds 64 four-bit values, so the PCU has 64 multipliers: 4× HBM-PIM's 16 FP16 multipliers (§V-A).

A 64-wide SIMD unit would need 64 accumulators of 32 bits. P3-LLM keeps 16 outputs and widens the input instead. HBM-PIM's tile is 1×1×16.

Each PE multiplies in 6-bit fixed point, shifts each product by the input's exponent, adds the four in a 4:2 compressor tree and accumulates in 32 bits.

The PE has no floating-point multipliers and no exponent alignment. It does 4 MACs per cycle at 1.08× the area of an FP16 PE (Table VIII).

15 / 21Part 4 of 6 · Design · 2: PCU and TEP

TEP clocks the PCU at tCCD_S, so each weight column, read once per tCCD_L, serves two input vectors.

Before you press play: at batch 1 there is only one input vector. What does P3-LLM's PCU do in the second tCCD_S slot of each window?

Nothing (frame 6). TEP needs a second input that uses the same weights. This is why P3-LLM's speedup peaks at batch 2 (Fig. 9).

HBM-PIM's PCU runs once per tCCD_L: each PIM command reads 256 bits of weights and does one GEMV step (§V-D).

The small PCU closes timing at tCCD_S, about half of tCCD_L. So within one window it multiplies weight W1 by input A, then by input B. Fig. 7 draws one PIM command per input.

The paper rejects two spatial options: an n×4×16 tile needs n× the multipliers, and an n×4×(16/n) tile wastes the 256-bit column.

PIM power rises only 28 %, because cell access and column decoding dominate it and do not change (§V-D).

16 / 21Part 4 of 6 · Design · 3: dataflow

The NPU keeps the FP16 operators and the dequantization, and P3-LLM folds each scale into a neighbouring operator, so PIM computes only in low precision.

The NPU runs LayerNorm, RoPE, softmax and the element-wise work in FP16/FP32. PIM runs every linear layer and P·V (Fig. 6b).

Q·Kᵀ runs on PIM only for keys quantized after RoPE (Llama-3, Mistral). Pre-RoPE keys (Llama-1/2) need RoPE on every stored key in every step, so the NPU does Q·Kᵀ.

Linear layers: the NPU multiplies the output by the scale after the matmul. Q·Kᵀ: the key smoothing factor S_SF is folded into the query before its FP8 cast.

P·V: the value scale S_V is folded into the scores, after division by its maximum S_Vmax so the scores stay in [0, 1]. The NPU multiplies S_Vmax back after P·V (§V-C).

17 / 21Part 5 of 6 · Evaluation

The evaluation simulates 4 NPU cores with 16 HBM2 pseudo-channels and compares P3-LLM against three systems with the same NPU and DRAM.

The PCU is RTL synthesized in TSMC 28 nm, scaled to HBM-PIM's 20 nm with DeepScaleTool, then given a 10× penalty for the DRAM process. An in-house cycle-level simulator runs the system (§VI-A).

The NPU runs at 1 GHz. The PCU runs at 500 MHz, which is HBM2's tCCD_S of 2 DRAM clocks.

Speed and energy: decoding only, 4K context, batch 1–8, five models (Llama-2 7B and 13B, Llama-3.1-8B, Llama-3.2-3B, Mistral-7B v0.3).

Accuracy: eight models, perplexity on Wikitext-2 and C4 at 2K context, plus MMLU, ARC-Challenge and GSM8K.

18 / 21Part 5 of 6 · Evaluation

Even with more operands quantized, P3-LLM loses less perplexity than QuaRot and QoQ.

KV-cache only: P3-LLM loses 0.06 on Wikitext against Oaken's 0.08 (Table IV).

With weights and activations quantized, P3-LLM loses 39 % and 22 % less perplexity than QuaRot and QoQ. Those two keep the query and the scores in FP16.

Reasoning tasks, averaged over MMLU, ARC-C and GSM8K on two instruct models: P3-LLM 73.69, QuaRot 71.12, QoQ 70.64, FP16 76.30 (Table V).

The gap is largest on Llama-3.2-3B, where calibrated integer methods overfit (§VI-B).

19 / 21Part 5 of 6 · Evaluation

Across batch 1–8 at 4K context, P3-LLM averages 4.9× the speed and 3.5× the energy efficiency of HBM-PIM.

HBM-PIM beats the NPU only at batch 1–2. Its edge fades at batch 4 and disappears for GQA models (Fig. 9).

P3-LLM's speedup peaks at batch 2, where TEP fills both tCCD_S slots.

Energy falls because 4-bit operands cut DRAM traffic and the PCU is cheaper. HBM-PIM re-reads the weights for each request; TEP halves that repeat (Fig. 10).

P3-LLM is also 3.4× faster than Pimba enhanced to W8A8KV8 (Fig. 12). From batch 8, P3-LLM moves the linear layers back to the NPU (Fig. 16).

20 / 21Part 5 of 6 · Evaluation

The wider PCU costs 1.1 points of HBM die area: 17.5 % against HBM-PIM's 16.4 %.

PCU compute area grows from 7.7 to 8.4 mm². The buffer stays at 6.2 mm² (Table VII).

Per PE, P3-LLM does 4 MACs per cycle at 0.18 pJ per MAC: 3.8× better energy per MAC than the FP16 PE (Table VIII).

The count includes only HBM-PIM's MAC hardware. Its instruction decoder and other operators are left out (§VI-C).

21 / 21Part 6 of 6 · Discussion · [BRAINSTORM]

Points to discuss: quantization gives most of the gain, and TEP, the PIM-side idea, stops at two inputs per weight read.

[BRAINSTORM] Our reading, not the paper's claims

  1. Where the speedup comes from. W4A8KV4 alone gives 3.3× over FP16 HBM-PIM; TEP adds 1.6×. A baseline already at 4-bit weights would shrink the headline.
  2. Would a DRAM vendor accept TEP? It needs the PCU to close timing at tCCD_S (500 MHz on HBM2) and a weight slice to stay valid for a whole tCCD_L.
  3. One command per input. Fig. 7 draws a separate PIM command per input vector, so deeper reuse would need more command slots. TEP reaches depth 2, and from batch 8 the linear layers leave PIM. Our group's CoDe work studies this command-bound limit.
  4. "Edge" means HBM2 here. The paper says TEP carries over to LPDDR, where tCCD_S is half of tCCD_L, but does not evaluate it.
  5. Frozen smoothing factors. The paper does not say what happens when a decode-time key exceeds the prefill maximum. Pre- or post-RoPE is chosen per model family; pre-RoPE models keep Q·Kᵀ on the NPU (Fig. 11).
  6. Model outputs, not silicon. An in-house simulator and a flat 10× DRAM penalty give the absolute numbers. Accuracy uses 2K context; speed uses 4K.
